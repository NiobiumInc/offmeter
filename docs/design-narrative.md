# Design Narrative: Demand-Response Eligibility under FHE
_Generated by the Niobium FHE Application Design AI Assistant (FHEanna)._ (v0.13.0)

This is the "why it looks the way it does" companion to the code. It walks the
ten-stage methodology as applied to one workload: scoring a household's
**encrypted** 24-hour electricity-usage profile against a utility's fixed
**demand-response eligibility** model, without the utility ever seeing the
profile.

Three versions of the program are kept distinct throughout (per the methodology):

- **reference**: the ideal plaintext model, a logistic regression over the 24
  hourly values plus two derived aggregates, followed by a true sigmoid.
- **twin**: the *faithful twin*, the same linear algebra but with the sigmoid
  replaced by the exact degree-13 Chebyshev interpolant the encrypted circuit
  evaluates. It is the executable spec.
- **FHE program**: the four-program OpenFHE implementation in `app/`.

Fully Homomorphic Encryption (FHE) is the umbrella technique: computing on data
while it stays encrypted. CKKS is the specific scheme used here (approximate
arithmetic on real numbers).

## Stage 1: Privacy model

- **Parties.** A *household* (the client / data owner / decryptor) and the
  *utility* (the server / compute party). The household holds a private 24-value
  hourly kWh profile. The utility holds the model (weights, bias, the two
  aggregation windows). These are fixed and known to the
  utility, i.e. **not secret**, so they are plaintext operands.
- **Adversary.** A semi-honest utility: it runs the computation correctly but
  may try to learn the household's consumption. The profile, the two
  intermediate aggregates, and the sigmoid input/output must stay hidden from
  the utility.
- **Who encrypts / cadence.** Each household encrypts *its own* profile
  (**independent encryptors**) and is scored **one query at a time**
  (interactive). Together these set **`packing_mode = per_record`**: one
  household is one ciphertext; different households can never share a ciphertext
  (that would require sharing keys).
- **Who decrypts / output privacy.** The household holds the only secret key,
  decrypts its own probability, and thresholds at 0.5. The decryptor *is* the
  consumer of the result, so there is **no output-integrity problem** and **no
  transciphering** is needed. Output privacy is a non-issue in the single-query
  self-scoring model (the household only ever learns its own eligibility).
- **Clear/encrypted decomposition.**
  - `client_clear`: the household holds and encrypts its own profile.
  - `server_encrypted`: the whole scoring computation (aggregates + linear model
    + sigmoid): sensitive, must run server-side, and FHE-feasible.
  - `server_clear`: none. Every value the server touches is sensitive.

## Stage 2: Feasibility

1. **Data-oblivious?** Yes. The operation sequence is fixed: two sums, one
   weighted sum, one sigmoid. No branch depends on an encrypted value.
2. **One lane?** Pure CKKS arithmetic (adds, ciphertext×plaintext multiplies,
   one polynomial activation). No arithmetic↔boolean crossing.
3. **Depth?** Shallow: one multiply for the masked/weighted operands, one mask
   before the activation, and a degree-13 sigmoid (~5 levels). Well under the
   no-bootstrap ceiling (~depth 25–30 at N = 2^16). **No bootstrapping.**
4. **SIMD?** `per_record` uses only 24 of 32,768 slots (0.07% utilisation), a
   real and acknowledged cost of the independent-encryptor model. Throughput
   comes from task-level concurrency (many households on separate threads)
   rather than from packing. (A single-encryptor deployment that owned many households could
   pack them at a 32-slot stride and reuse the same window-32 rotate-and-sum; out
   of scope here because households are independent encryptors.)

## Stage 3: Plaintext algorithm and the activation-range gate

The model:

```
total_daily  = sum_{h=0..23} x[h]
evening_peak = sum_{h=17..21} x[h]
logit        = w_hourly · x + w_total · total_daily + w_peak · evening_peak + bias
prob         = sigmoid(logit)          eligible := prob > 0.5
```

There is no data-dependent control flow to remove; the model is already a fixed
arithmetic expression. The one non-linearity is the sigmoid.

**Activation-range feasibility check (the gate).** The decisive precondition is
that the sigmoid's input (the logit) stays in a compact band on representative
data. Measured on the 200-household training set: logit ∈ **[−5.81, 6.04]**,
std 3.0; on the test set **[−5.38, 5.74]**. The chosen sigmoid domain **[−8, 8]**
covers this with margin → **grade: EASY** (bulk in band, no tail). No filter and
no model change are required; a low-degree polynomial suffices. (Because the
grade is EASY, the `feature_bounds.csv` / two-threshold filter machinery from the
methodology is intentionally not instantiated: there is nothing to reject.)

*Reference/test data are seeded synthetic* (`model/make_model_and_data.py`, seed
`20260730`): 24-hour profiles built from an always-on base load, a morning bump,
a variable evening peak, and midday use plus noise. The model weights favour
evening-peak-concentrated consumption (good load-shedding candidates) and lightly
penalise midday-heavy and very-high-total use; a global scale + bias were
calibrated so logits sit in the band and eligibility is ~50%.

## Stage 4: Scheme

**CKKS.** The data is real-valued (kWh), the output is a probability, and small
approximation error is acceptable (the decision is a 0.5 threshold with a healthy
margin). Exact integer arithmetic (BFV/BGV) is unnecessary.

## Stage 5: Homomorphic circuit

**Boundary representation.** One ciphertext carries the 24 hourly values in slots
0..23 (the rest zero). This is the natural per-record layout and makes the two
aggregates cheap sums over slots.

**Computing the aggregates in-circuit (the crux of the problem).** Both derived
aggregates are computed *inside* the encrypted circuit from the encrypted vector,
never by the client:

- `total_daily` = **rotate-and-sum** of the ciphertext over a 32-slot window
  (rotate by 1,2,4,8,16 and add). Slot 0 accumulates slots 0..31; since only
  0..23 are non-zero, slot 0 = the day's total. Zero multiplicative depth.
- `evening_peak` = the same rotate-and-sum applied after a **mask** that keeps
  only hours 17..21. One multiply.

Each aggregate's fixed model weight is *folded into the plaintext mask* used for
its rotate-and-sum: multiplying the encrypted vector by a plaintext that holds
`w_total` in slots 0..23 (resp. `w_peak` in slots 17..21) and summing yields
`w_total · total_daily` (resp. `w_peak · evening_peak`) directly. The aggregate
is still derived in-circuit, and no extra depth or scalar multiply is spent.
The hourly term is the same masked-multiply-and-sum with the `w_hourly` vector.

**Assembling the logit and the activation.** The three summed contributions plus
a slot-0 bias plaintext give the logit in slot 0. Rotate-and-sum leaves partial
sums in the other slots, which are out of the sigmoid domain, so the logit is
**masked to slot 0** before the activation (the methodology's rule: keep every
slot fed to an in-circuit activation inside `[lo,hi]`, or `Decode` fails). The
masked-out slots become sigmoid(0)=0.5 and are ignored; slot 0 carries the
answer. The sigmoid is OpenFHE `EvalLogistic(logit0, −8, 8, 13)`.

**Rotations/keys.** Rotation keys for {1,2,4,8,16} (rotate-and-sum) and one
relinearization key (the sigmoid's internal ciphertext squarings). No other
rotation amounts; linear layers are rotation-free ciphertext×plaintext
multiply-accumulate.

**Depth budget.** masked multiply (1) → slot-0 mask (1) → degree-13 sigmoid
(ceil(log2(14))+1 = 5) ≈ 7 levels used; budget set to 12 for FLEXIBLEAUTO
headroom. The output ciphertext is measured at ~7 RNS limbs (levels consumed),
which the boundary-size measurement confirms.

## Stage 6: Parameters

| Parameter | Value | Rationale |
|---|---|---|
| Scheme | CKKS | real-valued, approximate |
| Ring dimension N | **2^16 = 65536** | backend floor; also required for 128-bit at this logQ. Set explicitly. |
| Multiplicative depth | 12 | ~7 used + headroom (FLEXIBLEAUTO can undercount by a level) |
| Scaling modulus | 50 bits | per-level precision |
| First modulus | 55 bits | initial headroom |
| Security | HEStd_128_classic | standard target |
| Scaling technique | FLEXIBLEAUTO | automatic rescaling |
| Rotation keys | {1,2,4,8,16} | window-32 rotate-and-sum |

logQ ≈ 55 + 12·50 = 655, which at 128-bit forces N = 2^16 regardless of slot
count, consistent with the floor.

**Decode-safety (predicted from the twin, confirmed by the run).** ~7 levels
consumed against a depth-12 chain leaves ample spare; operands are small (logit
≤ ~6 in magnitude). The circuit was predicted decode-safe before the encrypted
run, and the run confirmed it (no overflow, tiny output error).

## Stage 7: Twin validation (the gate)

The twin (`model/twin.py`) uses the identical linear algebra and the identical
degree-13 Chebyshev interpolant of the logistic on [−8, 8], differing from the
reference *only* in true-vs-polynomial sigmoid. On the 200-household test set:

- max |prob_twin − prob_ref| = **2.96e-3**, mean **1.51e-3**
- decision agreement **100%** (0 flips), eligibility 46.5%
- **application-level noise tolerance** = min decision margin |prob−0.5| over the
  test set = **6.45e-3**. Encryption error below this flips no decisions; it is
  the objective pass bar for Stage 8/10.

This is an autonomous run: the twin clears the goal floor (0 flips, poly error <
margin), so the design proceeded to the encrypted build and the twin-vs-reference
result is recorded as a logged assumption.

## Stage 8 / 10: Implementation and validation

Four OpenFHE C++ programs (`keygen`, `encrypt`, `server`, `decrypt`) plus a
`run_test.sh` orchestrator and the `run-in-container.sh` wrapper. The circuit
lives once in `common.hpp::run_circuit`, called identically by the `--cpu` path
and the recording (`--sim` / Fog) path, so the modes cannot diverge. Results are
in `results-report.md`; the protocol and threat model in
`protocol-threat-model.md`.

### Implementation notes (addendum)

- `EvalAdd`/`EvalMult` take a non-const `Plaintext&`, so `run_circuit` takes the
  plaintext-operand struct by non-const reference (built once, tagged for the
  recorder before `start()`).
- Default (Fog) mode never silently falls back to the local simulator: with no
  API key it prints the sign-in pointer; with a key but not launched under
  `fog submit` it prints how to dispatch. Local validation is `--sim` / `--cpu`.
