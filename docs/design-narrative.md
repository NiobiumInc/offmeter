# Design Narrative: Demand-Response Eligibility under FHE
_Generated by the Niobium FHE Application Design AI Assistant (FHEanna)._ (v0.13.0)

This is the "why it looks the way it does" companion to the code. It walks the
ten-stage methodology as applied to one workload: scoring a household's
**encrypted** electricity-usage history against a utility's **confidential**
demand-response eligibility model, without the utility ever seeing the usage and
without the household ever seeing the model.

Three versions of the program are kept distinct throughout (per the methodology):

- **reference**: the ideal plaintext model, being the CalTRACK/TOWT derivation
  followed by the utility's logistic scoring layer and a true sigmoid.
- **twin**: the *faithful twin*, the same linear algebra but with the sigmoid
  replaced by the exact degree-13 Chebyshev interpolant the encrypted circuit
  evaluates. It is the executable spec.
- **FHE program**: the four-program OpenFHE implementation in `app/`.

Fully Homomorphic Encryption (FHE) is the umbrella technique: computing on data
while it stays encrypted. CKKS is the specific scheme used here (approximate
arithmetic on real numbers).

## Stage 1: Privacy model

- **Parties.** A *household* (the client / data owner / decryptor) and the
  *utility* (the server / compute party). The household holds a private 28-day
  hourly consumption series. The utility holds two things: a **public**
  derivation built from the calendar and public weather, and its **confidential**
  scoring weights.
- **Why the computation must happen server-side.** The scoring weights are the
  utility's own asset and are never disclosed to the household, so the household
  cannot compute its own score. The consumption series is the household's and is
  never disclosed to the utility, so the utility cannot compute it either. FHE is
  what lets the calculation happen at all.
- **Adversary.** A semi-honest utility: it runs the computation correctly but may
  try to learn the household's consumption. The series, the six derived
  quantities, and the sigmoid input/output must stay hidden from the utility.
- **Who encrypts / cadence.** Each household encrypts *its own* series
  (**independent encryptors**) and is scored **one query at a time**
  (interactive). Together these set **`packing_mode = per_record`**.
- **Who decrypts / output privacy.** The household holds the only secret key,
  decrypts its own probability, and thresholds at 0.5. The decryptor *is* the
  consumer of the result, so there is **no output-integrity problem** and **no
  transciphering** is needed.
- **Clear/encrypted decomposition.**
  - `client_clear`: the household holds and encrypts its own series. It needs
    nothing from the utility to do so, including the derivation.
  - `server_encrypted`: the whole scoring computation (derivation + linear model
    + sigmoid).
  - `server_clear`: none. Every value the server touches is sensitive.

## Stage 2: Feasibility

1. **Data-oblivious?** Yes. The operation sequence is fixed: six weighted sums,
   one shared slot-aggregation, one sigmoid. No branch depends on an encrypted
   value.
2. **One lane?** Pure CKKS arithmetic (adds, ciphertext×plaintext multiplies, one
   polynomial activation). No arithmetic↔boolean crossing.
3. **Depth?** Shallow: one multiply for the weighted rows, one mask before the
   activation, and a degree-13 sigmoid (~5 levels). ~7 levels total, well under
   the no-bootstrap ceiling (~depth 25–30 at N = 2^16). **No bootstrapping.**
4. **SIMD?** `per_record` uses 672 of 32,768 slots (2.1%), a real cost of the
   independent-encryptor model. Throughput comes from task-level concurrency.

## Stage 3: Plaintext algorithm and the activation-range gate

### Why this model form

Demand-response targeting has no standardised model of its own, but the quantity
it ranks on does: the hourly load impact, whose estimation is governed by the
CPUC Load Impact Protocols and implemented by the CalTRACK methods. Building the
derivation on that specification means the model form is one a utility analyst
already recognises, and its correctness can be checked against a published method
rather than against taste.

The structure has three parts:

- **The derivation** is the CalTRACK / OpenDSM **Time-of-Week & Temperature
  (TOWT)** model form: a least-squares regression of metered load on
  time-of-week indicators and piecewise-linear temperature terms. This is the
  hourly method behind CPUC-regulated demand-response and efficiency settlement,
  with an Apache-2.0 reference implementation.
  - CalTRACK methods: <https://docs.caltrack.org/en/latest/methods.html>
  - OpenDSM (LF Energy): <https://github.com/opendsm/opendsm>
  - CPUC Load Impact Protocols:
    <https://www.cpuc.ca.gov/industries-and-topics/electrical-energy/electric-costs/demand-response-dr/demand-response-load-impact-protocols>
- **The label** is a **measured** load impact. A demand-
  response event is simulated on a hot weekday; the household's Customer Baseline
  Load is computed 10-in-10 style (event hours averaged over the 10 most recent
  similar weekdays); the actual event load is subtracted; the household is
  eligible if the measured reduction clears a kW threshold. The label is produced
  by the *measurement protocol* applied to simulated behaviour.
- **The model** is the utility's confidential ridge-logistic scoring layer over
  the six derived quantities.

### The crux: why TOWT is FHE-friendly

TOWT's regressors are the **calendar** and the **weather**. Both are public. So
the coefficient map `M = (XᵀX)⁻¹Xᵀ` is computable in the clear, and every derived
quantity is a **public linear functional of the private consumption series**:

```
feature_j = row_j · y          row_j public, y encrypted
```

That is exactly plaintext-vector × ciphertext followed by a slot sum: one
multiply of depth, with no division and no comparison. The industry standard
happens to be the shape CKKS is best at.

The six derived quantities:

| # | Name | What it is |
|---|---|---|
| 1 | `cbl_peak` | the 10-in-10 Customer Baseline Load for the 5–9pm event window |
| 2 | `cool_slope_hi` | the TOWT coefficient on the 75–90 °F cooling term (the AC-load proxy) |
| 3 | `peak_towt_design` | TOWT-predicted event-window load at the 95 °F design condition |
| 4 | `daily_mean` | overall level (mean hourly kWh across the baseline) |
| 5 | `midday_mean` | daytime-occupancy proxy; daytime-heavy users shed less |
| 6 | `weekend_evening_delta` | weekend minus weekday evening load |

Both design matrices are rank-checked by assertion in the generator: the 672×51
TOWT matrix is full rank, and the six derived features are rank 6 with condition
number 4.9e3.

**Activation-range feasibility check (the gate).** Measured on the 400-household
test set: logit ∈ **[−3.11, 1.92]** (p0.1–p99.9 [−3.11, 1.90]); on the 3,000-
household training sample **[−3.16, 1.95]**, std 1.57. The sigmoid domain is set
from that measured range plus a one-unit margin: **[−5, 5]** → **grade: EASY**.
No filter and no model change are required.

The domain is matched to the operand range, which is what the methodology asks
for: a tighter interval is a better fit at a fixed degree. Widening it to [−8, 8]
at the same degree costs 2.96e-3 of polynomial error against the 1.58e-4
measured here.

*Data are seeded synthetic* (`model/make_model_and_data.py`, seed `20260808`):
synthetic hourly weather (seasonal drift + diurnal cycle + noise) and synthetic
households (always-on base, morning/evening/midday activity, weekend lift, and a
cooling slope, with 25% having no cooling at all). Event response is driven by a
`willingness` parameter that is **deliberately invisible in metered load**, which
is what caps how well any model fitted to the baseline period can predict it.

## Stage 4: Scheme

**CKKS.** The data is real-valued (kWh), the output is a probability, and small
approximation error is acceptable (the decision is a 0.5 threshold with a healthy
median margin). Exact integer arithmetic (BFV/BGV) is unnecessary, and BFV/BGV
would have no cheap sigmoid.

## Stage 5: Homomorphic circuit

**Boundary representation.** One ciphertext carries the 672 hourly values in
slots 0..671 (the rest zero). The client packs its own meter data and needs
nothing from the utility to do it.

**The circuit.** Each derived quantity gets its own ciphertext × plaintext
multiply against its own public row, with the confidential weight `w_j` folded
into that plaintext before encoding, so the derivation and the scoring cost one
multiply *total* per feature, at no extra depth. The six products are added, and
then a **single shared rotate-and-sum** over a 1024-slot window collapses them to
slot 0.

Sharing the slot-sum is exact, not an approximation: rotate-and-sum is linear, so
`Σⱼ rot_sum(x·pⱼ) = rot_sum(Σⱼ x·pⱼ)`. It replaces 60 rotations per record with
10, and measured end-to-end it cut the server from 43.8 s to 12.6 s per household
with bit-identical results.

**Assembling the logit and the activation.** Slot-0 bias, then mask to slot 0
before the activation (the methodology's rule: keep every slot fed to an
in-circuit activation inside `[lo,hi]`). The masked-out slots become
sigmoid(0)=0.5 and are ignored. The activation is `EvalLogistic(logit0, −5, 5, 13)`.

**Rotations/keys.** Rotation keys for {1,2,4,…,512} (the 1024-slot window) and one
relinearization key. The window is a client-side constant, so key generation
needs nothing from the utility.

**Depth budget.** masked multiply (1) → slot-0 mask (1) → degree-13 sigmoid
(ceil(log2(14))+1 = 5) ≈ 7 levels used; budget set to 12 for FLEXIBLEAUTO
headroom.

**On irreducibility.** Because every derived quantity is linear in `y`, the whole
circuit is algebraically equivalent to one dot product against `Σⱼ wⱼ·rowⱼ`.
Keeping the six derivations separate is a demonstration choice. The privacy claim
holds either way: the utility never sees the series, and the household never sees
the weights. An irreducible circuit would need a feature nonlinear in `y` (a ratio
such as load factor, or a baseline CV), which under CKKS means division.

## Stage 6: Parameters

| Parameter | Value | Rationale |
|---|---|---|
| Scheme | CKKS | real-valued, approximate |
| Ring dimension N | **2^16 = 65536** | fixed for this deployment; logQ ≈ 655 sits well inside the 128-bit ceiling at this N. Set explicitly. |
| Multiplicative depth | 12 | ~7 used + headroom (FLEXIBLEAUTO can undercount by a level) |
| Scaling modulus | 50 bits | per-level precision |
| First modulus | 55 bits | initial headroom |
| Security | HEStd_128_classic | standard target |
| Scaling technique | FLEXIBLEAUTO | automatic rescaling |
| Rotation keys | {1,2,4,…,512} | 1024-slot rotate-and-sum over a 672-hour series |

logQ ≈ 55 + 12·50 = 655. At N = 2^16 that sits well inside the
`HEStd_128_classic` ceiling, so the parameter set carries security headroom above
the 128-bit target rather than sitting at it. (The standard lattice tables already
admit N = 2^15 at this logQ; N = 2^16 is fixed for this deployment, and the cost
of that choice is ciphertext size and per-record time.)

Depth is likewise conservative: ~7 levels are used against a budget of 12. The
five spare levels add 250 bits to logQ (655 vs ~455) and correspondingly to
ciphertext size and runtime. A depth of 8–9 would retain FLEXIBLEAUTO headroom at
lower cost; 12 is kept here as margin.

The 1024-slot window sets the setup cost: ten rotation keys take the key bundle to
**607 MB**, once per session, for a 28-day baseline.

**Decode-safety (predicted from the twin, confirmed by the run).** ~7 levels
consumed against a depth-12 chain leaves ample spare; operands are small (the
generator reports max |w·row·y| per slot = 4.1e-1, and |logit| ≤ ~3.2). The
circuit was predicted decode-safe before the encrypted run, and every run
confirmed it.

## Stage 7: Twin validation (the gate)

The twin (`model/twin.py`) uses the identical derivation and linear algebra and
the identical degree-13 Chebyshev interpolant of the logistic on [−5, 5],
differing from the reference *only* in true-vs-polynomial sigmoid. On the
400-household test set:

- max |prob_twin − prob_ref| = **1.579e-4**, mean **7.381e-5**
- decision agreement **100%** (0 flips)
- **application-level noise tolerance** = min decision margin |prob−0.5| over the
  test set = **5.462e-5** (median margin 3.182e-1). `run_test.sh` reads this from
  `data/noise_tolerance.txt` rather than from prose.

The tolerance is smaller than the polynomial error, so the twin reports it
explicitly: **1 of 400** households sits closer to 0.5 than the polynomial error.
The twin agrees with the reference on every record here; for a household on the
boundary that agreement is a measured outcome on this seed.

## Stage 8 / 10: Implementation and validation

Four OpenFHE C++ programs (`keygen`, `encrypt`, `server`, `decrypt`) plus a
`run_test.sh` orchestrator and the `run-in-container.sh` wrapper. The circuit
lives once in `common.hpp::run_circuit`, called identically by the `--cpu` path
and the recording (`--sim` / Fog) path, so the modes cannot diverge. Results are
in `results-report.md`; the protocol and threat model in
`protocol-threat-model.md`.

### Implementation notes (addendum)

- `EvalAdd`/`EvalMult` take a non-const `Plaintext&`, so `run_circuit` takes the
  plaintext-operand struct by non-const reference (built once, tagged for the
  recorder before `start()`).
- The recorder tags each feature plaintext by name (`feat_<feature>`), so a trace
  is self-describing about which derived quantity each operand belongs to.
- Default (Fog) mode never silently falls back to the local simulator: with no
  API key it prints the sign-in pointer; with a key but not launched under
  `fog submit` it prints how to dispatch. Local validation is `--cpu` / `--sim` /
  `--sim-full`.
