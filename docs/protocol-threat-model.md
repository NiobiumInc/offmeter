# Protocol & Threat Model: Demand-Response Eligibility under FHE
_Generated by the Niobium FHE Application Design AI Assistant (FHEanna)._ (v0.13.0)

## Parties and hosts

| Party | Host | Holds |
|---|---|---|
| Household (client) | client host | crypto context, public key, **secret key**, its private 24-hour profile |
| Utility (server) | server host | crypto context, public key, evaluation keys (relin + rotation), the plaintext model: **no secret key, no client inputs** |

The server host is provisioned without the secret key and without any plaintext
input, so it is safe to place on untrusted infrastructure.

## Message flow

**Setup (once per session):**

1. Client runs `keygen`, producing the crypto context, public key, secret key,
   the relinearization key, and rotation keys {1,2,4,8,16}.
2. Client ships to the server, once: crypto context + public key + evaluation
   keys (~337 MB total). The **secret key never leaves the client.**
3. The server also holds the model (`model.txt`), public per the problem
   statement (weights and aggregation windows are known to the utility).

**Per request:**

4. Client → server: one input ciphertext (~13 MB) holding the encrypted 24-hour
   profile in slots 0..23.
5. Server computes the circuit under encryption (aggregates + linear model +
   sigmoid) and returns one output ciphertext (~7 MB), still encrypted.
6. Client decrypts slot 0, obtains the eligibility probability, thresholds at
   0.5.

Only ciphertext (and, at setup, public/eval keys) ever crosses the wire. The
server logs only byte counts ("received N bytes … still encrypted", "returned M
bytes … still encrypted").

## What each party can and cannot learn

- **Utility (semi-honest).** Sees ciphertext, the public/eval keys, and the
  public model. Learns **nothing** about the household's hourly profile, the two
  intermediate aggregates, the logit, or the probability; all remain encrypted
  under a key it does not hold. It learns only that a request occurred, and its
  timing/size (identical for every request: one ciphertext in, one out).
- **Household.** Learns its own eligibility probability and label. Since it owns
  the input, this reveals nothing it did not already have.

Assumption: semi-honest (honest-but-curious) server, standard CKKS/RLWE hardness
at 128-bit classical security.

## Intentional information leakage (the protocol output)

The one intended output is the household's own eligibility probability, revealed
only to the household. Nothing is revealed to the utility.

## Incidental leakage

- **Timing / size.** Constant across requests (fixed-shape circuit, one input and
  one output ciphertext), so they carry no data-dependent signal.
- **Request existence.** The utility learns that a household requested a score
  and when, not its contents.
- **No rejection channel.** Because the activation-range grade is EASY, there is
  no input-bounds filter and thus no rejection event to observe (contrast with
  workloads that leak a coarse decision boundary through rejections).

## Output integrity

**Not applicable.** The decryptor (household) *is* the consumer of the result.
It decrypts and acts on its own eligibility. There is no third party who must be
convinced the result is genuine, so no transciphering / dual-output layer is
needed. (If a deployment instead had the *utility* act on the score, output
integrity would return and a transciphering layer under a utility-held key would
be added; out of scope here.)

## Coverage / input-bounds filter

None. The Stage 3 activation-range check graded **EASY** (all logits within the
[−8, 8] sigmoid domain with margin on representative data), so no records are
filtered and there is no reject/fallback rate to report. A `per_record` deployment
would still wrap decrypt in a try/catch as a belt-and-braces fallback for a
pathological out-of-band household; none occurred in testing.

## Trust-boundary enforcement (tested)

- `keygen` writes the secret key **only** into the client home.
- `run_test.sh` provisions the server home with just the context, public/eval
  keys, model, and the input ciphertext, and asserts the secret key is absent.
- The **server refuses to start** if a `sk.bin` is present in its home. A
  reviewer can copy the secret key in and confirm the abort (the run_test
  negative test does exactly this and expects a non-zero exit).

## Threats not addressed

- **Malicious (not semi-honest) server.** Could return a wrong ciphertext;
  detecting that needs verifiable computation, not provided here.
- **Exhaustive / repeated queries.** A household querying many perturbed
  profiles could probe the decision boundary of the (public) model; rate limiting
  is a deployment concern.
- **Side channels** (timing beyond the coarse constants above, memory, power on
  the server host).
- **Collusion** and key management beyond the single-household model.
